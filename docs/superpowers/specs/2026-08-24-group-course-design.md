# 小程序单次公开团体教学课设计

日期：2026-08-24

修订日期：2026-09-05

设计状态：采用一次性发布并占场。管理员在创建表单填写内容，发布前通过弹框确认关键信息，确认后由服务端原子创建课程并占用全部时段；发布后不可修改，变更须整体取消后重新发布。本期不设置草稿状态、草稿保存或编辑流程。其他报名、定价、成班和自动退款规则按本文执行；本文为现行设计，代码已实施；验证与未部署边界见 [[court-book/团课部署与验收]]。

## 1. 目标

在现有微信小程序内增加单次公开团体教学课。具备畅打发起权限的管理员填写课程信息，经发布前弹框确认后一次性发布并占场；用户以本人手机号报名并通过微信支付取得名额。系统必须处理名额并发、课程最低人数、自动取消、全额退款，以及受小程序管理场地的占用和释放。

团课是独立的 CloudBase 子系统。它不复用畅打业务代码，不读写远端 MySQL 的课程、教练或会员课程表，也不进入现有教练正式课程和月度授课统计。

## 2. 非目标

- 不设计课程页面的最终视觉样式，也不使用课程图片或教练头像作为课程主图。
- 不做固定周期班、多场次课程包、多人代报、候补、签到或教练端入口。
- 不设置草稿状态、保存草稿、编辑已有课程或删除草稿流程；发布前的输入仅为页面表单状态。
- 不允许管理员修改已发布课程，包括教学内容和开课安排。
- 本期不做免费课，不新增校区、场地、教练或教学内容模板的管理页面；这些基础资料直接在云数据库中维护。
- 不同步远端 MySQL 正式课程。
- 不发送小程序订阅消息；微信支付渠道自行发送支付和退款通知。
- 不改造普通订场和畅打业务流程。团课仅在受管理校区正式发布时占场、课程取消时释放；填写表单和查看确认弹框不写入场地占用。
- 自动测试不连接真实 CloudBase、微信支付或测试数据库。
- 本期按正常支付成功后 1 分钟内完成回调处理的业务假设设计；不增加旧报名轮次迟到付款的专门隔离、自动退款或跨轮次补偿流程。超过该窗口的云服务或支付通知异常不纳入本期自动处理范围，发生后向相关服务商反馈排查。该取舍不等于已取得厂商时限保证或责任承诺。

## 3. 已确认业务规则

### 3.1 发布与课程

- 团课由管理员在小程序发布，权限与畅打发起一致：`courtRushManager >= 1` 或 `specialManager >= 1`。
- 管理员填写新课程表单，选择教学内容模板并填写开课安排；正式提交前弹框确认关键信息。填写、选择时间或查看弹框均不创建课程记录，也不占场。
- 管理员点击弹框中的“确认发布”后，服务端一次性创建 `PUBLISHED` 课程并占用所需全部时段。课程创建和受管理场地占用在同一事务中提交，任一失败全部回滚，不留下部分课程或部分占场。
- 发布只能发生在报名截止前，即服务端发布事务内当前时间必须严格早于 `startAt - 1 小时`。到达或超过该时间拒绝发布，管理员可在尚未提交成功的表单中调整时间，再次确认后提交。
- 课程一旦发布，标题、详情、教练、校区、场地、时间、价格、最低人数和人数上限均不可修改。需要变更时整体取消原课程，再创建并发布新课程；原课程及报名退款历史保留。
- 每节课关联一位 CloudBase `manager` 中的授课人员（`name`、`phoneNumber` 均为非空字符串）。不新增教练标记、启用字段或独立 `coach` 集合。教练仅作为课程展示数据，不获得团课页面或报名名单入口。
- 每节课只能选择一个校区、一个场地和同一自然日内的一段连续时间，起止时间按 30 分钟对齐，结束时间晚于开始时间。
- 同一教练的团课时间不能重叠；同一校区同一场地的团课时间不能重叠；同一校区不同场地可以同时开课。冲突按 `[startAt, endAt)` 判断，相邻课程不视为重叠。
- 业务前提：只有一位管理员，团课发布与取消、畅打发起及管理员订场等人工场地操作串行完成；上一操作明确结束后才进行下一操作。教练与团课内部场地冲突采用发布时查询校验，不增加独立资源卡位集合。
- 单管理员前提不排除普通用户订场、报名、支付回调和定时任务并发；发布时仍须在事务中校验场地，不能以确认弹框出现时的查询结果代替提交时的检查。
- 管理员可以在课程发布后任何时候整体取消，包括课程已经开始或完成之后。本期统一使用“取消课程”和 `CANCELLED`，暂不区分未开课取消、上课中止与课后全额退款；不能仅凭 `CANCELLED` 推断课程实际未发生。

### 3.2 校区与场地

- 新建 CloudBase `campus` 集合，字段仅为 `name`、`enabled`、`sortOrder`、`bookingManaged`。
- `campus` 是团课可选校区集合，也是现有 `court` 集合中校区的超集。
- 场地列表继续从现有 `court` 集合按所选 `campus` 查询，不改变 `court` 的现有校区逻辑。
- 校区、场地和教练资料本期直接在云数据库维护，不新增管理页面。仅当 `bookingManaged=false` 且该校区没有任何 `court` 记录时，服务端提供“1号场、2号场”，不创建 court 记录。默认 courtId 为 `group_course_default_` + `hash(campus.name, courtNumber)`（SHA-256 摘要前32位），按校区与编号固定。发布时重新校验条件与标识。有真实 court 记录时只允许真实场地；受管理校区不提供默认场地。冲突按校区、场地编号和时间判断，后续补录同编号真实场地也不能绕过历史课程冲突。
- `bookingManaged=false` 时，发布仅在团课内部保存资源安排，不写入订场占用集合；发布成功的课程参与其他团课的资源冲突判断。
- `bookingManaged=true` 时，课程发布和取消与现有 `court_order_collection` 交互。该集合是普通订场、畅打和团课共同的场地占用记录；人工操作遵循第 3.1 节的唯一管理员串行操作前提。
- 发布时课程创建与全部时段占用使用同一事务保证原子性；取消后的归属检查与释放可由维护任务补做，保留 `(campus, court_id)` 唯一索引防止重复插入。复用或释放已有记录时递增现有 `version`，与普通订场的版本检查保持一致。唯一索引本身不防止覆盖；本期仍以单管理员串行操作为前提，不宣称已改造全部跨业务写入。

### 3.3 报名、价格和名额

- 一个手机号在一节课程中只能有一条报名记录，只能为本人报名一个名额。
- 团课登录与畅打保持一致，直接复用个人中心手机号与全局头像昵称；资料缺失才跳个人中心。管理员与 VIP 仍服务端查库，不另建团课登录 token 或身份表。
- 报名业务身份使用手机号，不使用 `openid`。微信 JSAPI 下单需要 `openid` 时，云函数从微信上下文临时取得，且不把它作为报名业务键。
- VIP 判定沿用现有畅打规则：手机号对应的会员账户余额、次卡或年卡折算价值大于 0 时视为 VIP。
- 本期只做付费课。管理员分别手填原价 `priceYuan` 与 VIP 实付金额 `vipPriceYuan`，均为至少1元的整数，VIP 不高于原价，转分后为安全整数。VIP 支付手填金额，不设置默认折扣。发布时服务端校验并保存两项金额快照，发布后不可修改。
- 新报名在开课前 1 小时截止。服务端在截止时间前接受了报名占位后，后续付款不再受报名截止限制。
- 微信付款单有效期为创建后 2 分钟。过期后不能继续支付，也不能在原占位内生成新付款单。
- 名额占位从本轮报名开始起保留 3 分钟。第 2 至第 3 分钟用于等待回调和主动查单；3 分钟到期仍未确认支付成功则占位失效，不因查单失败或结果未明无限期保留。失效表示本系统未确认报名成功，不代表支付渠道必然没有收款；超出正常回调窗口的异常按本期非目标处理。
- 占位释放后，只要未到报名截止时间且课程未满，用户可以重新发起一轮报名。
- 不做候补。只要当前有效占位未达到上限，其他用户就可以报名。
- `group_course` 不保存 `heldCount`、`paidCount` 或其他参与人数缓存。展示人数、占用名额和最低开课人数均聚合个人报名记录得出。

### 3.4 取消、成班与退款

- 用户可在开课前 12 小时之外自助取消，按实际支付金额发起全额原路退款，不收手续费。
- 只有通过微信退款成功回调或主动查询确认退款成功后才释放名额。退款处理中或退款失败时仍占用名额。
- 退款成功释放名额后，只要未到报名截止时间且课程未满，课程自动恢复可报名。
- 成班最终判定时间固定为报名截止时间加 3 分钟，即 `startAt - 1 小时 + 3 分钟`。到点触发判定，按实际执行确认时当前状态为 `PAID` 的报名人数判断，不筛选 `paidAt`：达到最低人数则成班，未达到则自动整体取消并逐笔退款。支付查单失败或结果不明确不得延长此期限，未确认付款不计入最低人数。
- 课程因人数不足取消后，不因迟到的支付确认恢复课程；正常支付流程中课程取消与支付确认并发时，仍按第 7.3 节全额退款。超出正常回调窗口的旧轮次付款不另设自动退款流程；成班人数以实际执行确认时的报名状态为依据，具体见第 7.6 节。
- 管理员整体取消时立即禁止新报名并释放受管理场地；已支付报名随后逐笔退款。课程取消不等待退款全部完成。
- 退款采用持久化任务加每分钟定时执行的机制，自动补漏、查询和重试，不提供管理员手动重试入口。本期复用退款集合承载任务，不额外部署独立消息队列服务。
- 明确不可自动恢复的退款异常仅写后台日志，并更新现有退款记录的状态、渠道状态和错误字段；不新增异常集合、异常记录、异常展示页面或额外处理入口。
- 课程、报名、支付和退款记录均不物理删除。普通公开列表不显示已取消课程；报名用户在“我的团课”中仍能查看已取消课程和退款状态。

### 3.5 教学内容模板与基础资料维护

- 新建 CloudBase `group_course_template` 集合，作为教学内容模板的独立持久化数据表，不使用前端硬编码列表。
- **教学内容模板（course template）**：描述课程要教什么的可复用内容，包含标题和教学详情。例如“正手击球入门”，详情说明教学目标、练习内容等。管理员选择后，将这些内容填入具体课程的数据。
- **具体课程**：一节正式发布后接受报名的授课安排，创建课程记录与占场一次性完成。课时时长、价格、最低人数、人数上限、日期、开始与结束时间、教练、校区和场地均属于具体课程，不属于教学内容模板，也不由模板预设。
- 校区、场地、教练与教学内容模板均直接在云数据库维护，本期不新增小程序管理页面。
- 模板用于带入课程内容，课程保存模板来源 ID 和自身内容快照。模板修改、停用不自动修改已经保存的课程内容，尤其不能绕过已发布课程不可修改的规则。
- 模板选择只填充新课程表单的标题和教学详情；发布前可调整表单内容。切换模板只替换教学内容，不改动已填写的时间、价格、人数、教练、校区和场地，也不回写模板。正式发布后这些内容均不可修改。

## 4. 架构与组件

### 4.1 页面

- `pages/groupCourse/groupCourse`
  - 同一页面切换“团课列表”和“我的团课”。
  - 普通公开列表不显示已取消课程。
  - 管理员在同一页面额外看到已取消课程和创建入口，不增加独立管理列表。
- `pages/groupCourseDetail/groupCourseDetail`
  - 用户查看课程、报名、支付和退款状态。
  - 管理员额外查看完整报名名单、整体取消和退款进度；不提供课程编辑、退款异常详情或手动重试入口。
- `pages/groupCourseForm/groupCourseForm`
  - 仅用于管理员创建并发布新课程，不接收已有课程进入编辑状态。
  - 选择教学内容模板，填写教学内容和开课安排；输入仅保留在当前页面，未提交不创建课程、不占场。
  - 点击“发布”先校验表单并展示第 7.1.1 节确认弹框，只有点击“确认发布”才调用服务端。
  - 弹框返回继续填写时不提交；表单内容改变后须重新展示对应确认信息。
  - 正式提交期间禁用重复点击。成功后进入课程详情；明确失败时保留当前页面输入，显示冲突时段或其他原因，不提示发布成功。
  - 响应丢失或结果未明时，沿用同一请求标识核实发布结果，不立即以新标识重新创建课程，见第 7.1.3 节。

具体页面视觉布局不在本设计范围内，但上述发布确认交互属于本期必需功能。

### 4.2 云函数

只新增四个云函数：

1. `group_course`
   - 通过 `action` 分发普通业务：`context`、`list`、`detail`、`publish`、`enroll`、`cancelEnrollment`、`cancelCourse`。
   - `context` 为管理员课程表单返回基础资料及启用的教学内容模板，不增加模板管理写入接口。
   - 入口文件只负责输入规范化、鉴权和分发；校验、仓储、定价、报名事务、发布事务、退款等拆成团课内部模块。
2. `group_course_payment_callback`
   - 微信支付成功的权威回调入口，独立部署并保持幂等。
3. `group_course_refund_callback`
   - 微信退款结果的权威回调入口，独立部署并保持幂等。
4. `group_course_maintenance`
   - 每分钟定时执行过期占位清理、未决支付查单、成班判断、最低人数自动取消、课程完成、取消收尾补漏及退款任务的领取、提交、查询和重试。

不增加独立 `group_course_pay_query`。前端支付成功后刷新详情；详情可在付款创建后的 2 分钟内向报名本人返回原支付参数。定时任务内部的微信主动查单不暴露为用户接口。

接口字段、共用个人中心登录、分页与独立部署合同详见 [[court-book/团课接口与数据契约]]；UI及跳转文字已按一次性发布流程同步。

### 4.3 权限边界

- 所有业务集合禁止小程序端直接写入；写操作全部经过云函数。
- 服务端每次管理员操作都重新查询 `manager` 集合，不能依赖前端隐藏按钮或全局缓存。
- 普通用户不能读取管理员操作字段、其他用户完整手机号或退款错误详情；未发布的表单输入不形成可读取的课程记录。
- 已取消课程详情只允许报名过的手机号和管理员读取。

## 5. 数据模型

### 5.1 `campus`

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 校区名称 |
| `enabled` | boolean | 是否可用于团课 |
| `sortOrder` | number | 展示顺序 |
| `bookingManaged` | boolean | 是否需要与现有订场系统交互 |

### 5.2 `group_course`

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 课程 ID |
| `status` | string | `PUBLISHED`、`CONFIRMED`、`COMPLETED`、`CANCELLED`；首次创建即为 `PUBLISHED` |
| `templateId` | string | 所选教学内容模板 ID，用于来源追溯；课程展示使用自身字段快照 |
| `title` / `description` | string | 从模板带入的课程标题和详情快照 |
| `coachId` / `coachName` | string | manager._id（授课人员资料引用）和 manager.name 发布快照 |
| `campus` / `courtId` / `courtNumber` | string | 校区与场地快照；courtId通常指向court._id，无场地的未管理校区使用第3.2节默认标识 |
| `bookingManaged` | boolean | 正式发布时校区管理方式快照，发布后固定；取消时按该快照与实际归属释放占用 |
| `courtIds` | string[] | 与课程发布同事务取得的连续半小时时段业务键；未管理校区为空数组 |
| `startAt` / `endAt` | Date | 课程起止时间 |
| `minParticipants` / `maxParticipants` | number | 最低开课人数和人数上限 |
| `priceYuan` | number | 手填原价，整数元且至少1元 |
| `vipPriceYuan` | number | 必填VIP实付金额，整数元且至少1元，不高于原价 |
| `enrollmentVersion` | number | 报名状态乐观锁版本，不表示人数 |
| `publishRequestId` | string | 单次确认发布的请求标识，用于重复提交及响应丢失后的幂等定位 |
| `publishPayloadHash` | string | 已确认发布内容的规范化摘要；同一请求标识不得用于不同内容 |
| `createdBy` / `publishedBy` / `cancelledBy` | string | 对应管理员手机号；创建与发布为同一操作 |
| `createdAt` / `updatedAt` / `publishedAt` / `cancelledAt` | Date | 状态时间 |
| `cancelReason` | string | 管理取消或最低人数不足原因 |

## 7. 关键流程

### 7.1 确认发布与原子占场

#### 7.1.1 发布前确认弹框

1. 管理员在创建表单中选用教学内容模板，确认标题与教学详情，并填写教练、校区、场地、日期、开始和结束时间、原价、最低人数与人数上限。
2. 点击“发布”时先做表单校验，再弹出关键信息确认框，集中显示：课程标题及教学内容摘要、教练、校区与场地、日期及起止时间和时长、非 VIP 原价与 VIP 实付价、最低人数与人数上限、报名截止时间。
3. 弹框明确提示：“确认后立即发布并占用场地，发布后不可修改；需要变更请整体取消后重新发布。” 对不受订场管理的校区，应按实际管理方式说明只记录团课场地安排，避免声称占用了订场系统。
4. 提供“返回修改”和“确认发布”两个操作。“返回修改”关闭弹框回到当前表单，不调用发布接口、不占场。
5. “确认发布”提交与弹框一致的内容快照。弹框打开后不能在后台悄悄替换已确认内容；若更换模板或修改表单，再次发布时必须重新确认。服务端不以重新读取模板覆盖管理员已经确认的标题和详情。
6. 确认弹框只帮助核对信息，不锁定资源；管理员点击确认后仍以服务端事务校验结果为准。

#### 7.1.2 服务端发布事务

1. `publish` 每次重新查询管理员权限，规范化并校验完整输入。验证有效教练、启用校区及场地归属，读取 `bookingManaged`；最低人数和上限为正整数且最低人数不大于上限；原价与VIP金额均为至少1元的整数，VIP不高于原价，转分后为安全整数。
2. 校验同一自然日、连续半小时时段、结束晚于开始，以及当前时间严格早于 `startAt - 1 小时`。所有时段与日期使用北京时间和现有订场格式。
3. 先按第 7.1.3 节识别同次请求的已提交结果，再查询 `PUBLISHED`、`CONFIRMED` 课程的教练及同场地时间冲突，按 `[startAt,endAt)` 判断重叠。已取消课程不阻挡新发布；该跨课程查询遵循唯一管理员串行操作前提。
4. 为本次发布确定稳定课程 ID，并按现有规则生成全部 `court_id`。受管理校区先在事务外按 `(campus,court_id)` 定位已有时段文档，事务内按文档 ID 重读。仅 `free` 或不存在的时段可取得，任何已 `locked` 或 `booked` 的时段均拒绝新发布；不得覆盖其他业务占用。
5. 在同一事务中重查发布幂等结果和发布时间边界，创建 `PUBLISHED` 课程，保存管理员、模板来源、教学内容、教练与资源快照、价格人数及发布标识，并写入全部场地占用。新时段通过唯一索引防止重复插入；复用空闲记录时递增其现有 `version`。
6. 任一时段冲突、唯一索引冲突或事务失败，课程创建与本次全部占场一起回滚。前端保留当前页面输入，提示具体冲突或失败原因；不能出现已发布但未占满场地、或课程不存在却留下本次部分占场的状态。
7. `bookingManaged=false` 时，仅在事务中创建正式课程与资源快照，不写订场占用集合。发布后仍参与团课内部教练和场地冲突检查。
8. 事务成功后返回课程 ID 并进入详情；首次创建时间与发布时间属于同一次提交。发布成功后没有课程编辑接口，任何内容变更须整体取消并重新发布。

#### 7.1.3 重复提交与结果核实

- 每次确认发布生成 `publishRequestId`；同一份已确认内容的网络重试沿用该标识。服务端以管理员手机号与该标识定位同次提交，并保存规范化内容摘要，防止同一标识被用于不同内容。
- 同一请求已成功时返回已有课程及当前状态，不再次创建或占场，也不因课程后来取消而重新发布。重复请求应先识别已提交结果，不能先把自身成功占用判断为资源冲突。
- 请求超时或响应丢失不等于发布失败。页面保持该次请求标识，通过同一 `publish` 请求核实结果；不得在旧结果未明时换标识创建相同课程。
- 服务端在发布事务内再次检查课程或唯一发布标识，配合唯一索引处理重复请求竞争。检测到重复提交后读取原结果，不能留下重复课程。
- 管理员修改确认内容后属于新的发布意图，需重新确认并使用新标识；先前提交结果必须已明确。该机制不额外保存未发布的课程记录。

#### 7.1.4 共享占场记录契约

- 占场记录必须具备现有订场读取所需的 `court_id`、`campus`、`courtNumber`、`date`、`start_time`、`end_time`，沿用现有日期和时段键格式，不能仅写状态与课程 ID。
- 同时保存 `status=booked`、`source_type=GROUP_COURSE`、`group_course_id`、`booked_by`（管理员手机号）、`version` 及创建、更新时间；不创建普通订场支付订单，不使用普通用户待付款的临时 `locked` 状态。
- 新增占用初始化 `version=1`；复用空闲记录或取消释放已有占用时递增版本，与普通订场的版本条件更新保持一致。
- 取消释放时仅处理同时匹配本课程来源和 ID 的占用，清除本课程归属、恢复 `free`，保留时段基础字段和递增后的版本。后台改动校区管理方式不能导致遗忘本课程实际已取得的占用。
- 普通订场在预检查之后、写入之前发现时段已被占用时，必须返回逐项失败并停止进入付款；不得将空结果列表视为成功。管理员预订也不得在场地写入失败后建立普通订单。
- 本契约适配现有订场展示和版本检查。为防止旧普通订单的重复回调、取消或回滚误改后来团课占场，对旧订场写入和释放增加 `source_type != GROUP_COURSE` 条件，回滚增加本次版本与归属限制；不改变原订场计费、支付或取消业务规则，不重构畅打流程。单管理员串行前提继续适用。

### 7.2 无人数缓存的并发报名

`enrollmentVersion` 只作为乐观锁，不参与人数判断。

每次报名尝试执行以下重试循环：

1. 读取课程及当前 `enrollmentVersion`。
2. 聚合占用名额状态的 `group_course_enrollment`。
3. 校验课程可报名、报名截止、手机号唯一和聚合数量小于 `maxParticipants`。
4. 预先完成会员/VIP 查询、金额计算和商户订单号生成；事务内不调用外部接口。
5. 开启事务并按 ID 重读课程。如果版本或课程状态已变化，终止本轮并从第一步重新统计；事务内再次校验报名截止时间，不能因会员查询或重试耗时而在截止后新建占位。
6. 版本未变化时，按确定性“课程 + 手机号”定位报名记录，创建或重新激活报名，创建 `PENDING` 支付记录，并执行 `enrollmentVersion + 1`。
7. 事务提交后调用微信统一下单，再把支付参数写回支付记录。
8. 微信下单失败时运行补偿事务：支付改为 `FAILED`、报名改为 `EXPIRED`、`enrollmentVersion + 1`。
9. 写冲突有限次数重试；每次重试必须重新聚合，不能使用旧人数。

### 7.3 支付确认

> 范围已确认：按支付成功后 1 分钟内完成回调处理的业务假设执行正常流程，保留按支付单号定位与重复回调幂等；本期不增加旧轮次迟到付款的专门隔离与自动退款流程，不宣称覆盖超出该假设的异常。成班判定的时间依据与并发校验见第 7.6 节。

1. 前端取得支付参数后调用 `wx.requestPayment`。
2. 前端成功仅用于提示和刷新详情，不作为业务支付成功依据。
3. `group_course_payment_callback` 按 `outTradeNo` 唯一定位支付记录。
4. 在事务中只把 `PENDING` 支付改为 `PAIDED`，报名从 `PENDING_PAYMENT` 改为 `PAID`，由数据库写入本轮首次确认时间 `paidAt`，并执行 `enrollmentVersion + 1`。重复回调不重写确认时间；占位重新激活时清空上一轮的 `paidAt`，保持新一轮支付记录准确。
5. 重复回调直接返回成功，不重复改变报名。
6. 若课程在回调前已整体取消，仍确认真实付款，随后为该支付创建全额退款，不能忽略已收资金。

### 7.4 占位过期

1. 付款创建后 2 分钟，详情不再返回支付参数。
2. 报名开始后 3 分钟，维护任务先主动查询微信订单。
3. 已确认支付则走统一支付确认逻辑；否则在占位 3 分钟到期后通过事务把仍未确认的支付和报名改为 `EXPIRED`，并执行 `enrollmentVersion + 1`。此处 `EXPIRED` 表示本地流程超时，不作为渠道未收款的证明。
4. 查单失败或结果不明确不延长占位，也不延后成班判定；记录异常，按第 2 节约定的范围处理，不增加无限等待或旧轮次迟到付款自动退款流程。用户在未到报名截止且名额可用时可以重新报名。

### 7.5 用户取消

1. 服务端判断请求到达时间早于 `startAt - 12 小时`，且报名为 `PAID`。
2. 事务中创建唯一 `PENDING` 退款记录，设置 `nextAction=SUBMIT`、`nextRetryAt=当前时间`，把报名改为 `REFUNDING`，并执行 `enrollmentVersion + 1`。此事务提交即代表退款任务已持久入队。
3. 事务提交后可立即通过第 7.8 节同一任务执行器尝试领取和发起退款；即使当前请求退出，每分钟定时任务也会继续执行，不依赖本次请求完成。
4. 退款成功回调与主动查询共用幂等成功处理逻辑：事务中把退款改为 `SUCCESS`，仅在报名仍关联该 `refundId` 时把报名改为 `CANCELLED` 并执行 `enrollmentVersion + 1`，此时释放名额。成功状态不能被迟到的失败结果覆盖。
5. 退款失败在原退款记录中更新状态和错误字段，报名可显示 `REFUND_FAILED` 并继续占名额；可自动恢复的情况按第 7.8 节核实和重试，明确不可自动恢复的异常仅记录日志和数据库状态，不需要管理员手动操作。

### 7.6 最低人数、自动取消与完成

1. 报名截止为 `startAt - 1 小时`。
2. 最终判定时间为报名截止加 3 分钟。此前处理截止前开始的付款流程；到点必须作出成班或取消的业务判定，不以全部占位查单完成为前提。
3. 读取课程及 `enrollmentVersion`，聚合实际执行确认时本课程 `status=PAID` 的报名数，不检查每个人的 `paidAt`。未决付款不计入，不能用前端支付提示替代服务端已确认状态。定时任务延迟执行时，期间已确认且当前仍为 `PAID` 的报名也计入人数；报名截止时间不变。
   判定提交前，在事务中重读课程并确认仍为 `PUBLISHED`、版本与聚合前一致；版本变化则重新聚合，课程已取消或已成班则不覆盖。支付确认与判定均读写同一课程文档，以事务冲突和版本校验避免使用陈旧人数。
4. 达到 `minParticipants` 时把课程从 `PUBLISHED` 改为 `CONFIRMED`。
5. 未达到时以 `MIN_PARTICIPANTS_NOT_MET` 原因整体取消，释放受管理场地并为全部已支付报名创建退款。
6. `endAt` 到达后把 `CONFIRMED` 课程改为 `COMPLETED`。
7. 管理员仍可把 `COMPLETED` 课程整体取消并退款。

### 7.7 管理员整体取消

> 已确认：课程取消后由现有每分钟维护任务补做遗漏退款，退款任务自动执行与恢复，详见第 7.8 节。不依赖管理员再次点击取消或手动重试。

1. 条件更新课程为 `CANCELLED`，保存管理员、时间和原因，立即阻止新报名。
2. 按第 7.1.4 节释放同时匹配 `source_type=GROUP_COURSE` 和 `group_course_id` 的占场记录，恢复 `free`、清除本课程归属并递增版本；不得只按时间或 `court_id` 释放。
3. 把未支付占位改为失效；为已支付报名创建第 7.5 节同样的持久化全额退款任务，由统一执行器处理。
4. 已经处于退款流程的报名复用现有退款记录。
5. 课程取消不等待退款全部完成；管理员详情保留基本退款进度。技术错误仅保存在现有退款记录和后台日志，不增加异常详情或处理入口。
6. 课程一旦标记 `CANCELLED`，立即处理与后续维护均以该持久状态为依据继续补做，不能因课程已取消而直接跳过剩余工作。取消请求重复执行也须允许继续收尾。
7. 每分钟维护任务核对已取消课程的已确认支付记录与退款记录，补建并推进遗漏的全额退款；不能只扫描现有 `FAILED` 退款，因为中断时可能根本没有创建退款记录。一笔支付仍只对应一个全额退款记录。
8. 同一维护过程补做尚未完成的场地释放和未支付占位失效；释放场地继续严格匹配本课程的来源与课程 ID。单笔退款失败不能阻止其他报名的退款继续处理。上述恢复同样适用于最低人数不足导致的自动取消。


### 7.8 退款任务执行与自动恢复

退款记录同时承担持久化任务职责，提供类似消息队列的“至少执行一次”机制。无需新增云函数、独立队列服务或管理员重试接口。

1. **先保存任务，再调用渠道。** 用户取消通过事务创建退款任务；课程整体取消即使在创建任务前中断，也由第 7.7 节的支付与退款核对补齐。退款记录以 `paymentId` 唯一约束防重，整个退款任务沿用同一 `outRefundNo`。
2. **领取任务。** 执行器在事务中检查任务未成功、执行时间已到且无有效租约，然后写入新的 `leaseToken` 与 `leaseUntil`。建议初始租约 2 分钟；外部请求超时应短于租约。执行者退出后租约到期，其他执行者可自动接续。
3. **提交前留下未决标记。** 调用退款接口前持久化 `status=PROCESSING`、`nextAction=QUERY` 与最近执行时间，再在事务外调用渠道。即使调用前后中断，接续者也先查询原退款单；明确退款单不存在时才使用原商户退款单号重新提交，查单网络失败不能当作退款不存在。
4. **已受理不等于退款成功。** 渠道仍在处理则保持 `PROCESSING`，默认 1 分钟后查询；请求超时或响应丢失也转为查询，不直接换单再次退款。查询确认成功与成功回调共用第 7.5 节处理逻辑。
5. **自动重试。** 可重试的提交失败和查询异常按连续失败次数采用 1、5、15、60 分钟退避，此后每 60 分钟重试；正常查询到处理中时重置连续异常次数。达到重试次数不删除任务、不标记成功，也不要求管理员点击重试。明确不可自动恢复的渠道结果将原退款记录标为 `FAILED`，保存 `channelStatus`、`failureCode`、`failureMessage`，设置 `nextRetryAt=null` 并释放租约，同时记录后台日志。该任务暂停自动提交与查询，不新增异常记录、不要求管理员处理，也不能标为退款成功；普通网络失败或结果未知不得归入此类。
6. **防止旧执行结果覆盖。** 执行器回写时校验租约标识和当前状态；租约失效的执行者不能覆盖新执行结果。成功回调可以在任务执行期间将退款置为成功；之后任何执行器的失败或处理中结果都不得将其改回。租约只能减少重复执行，渠道提交仍依赖同一退款单号的幂等。
7. **完成与异常记录。** 只有渠道明确成功才把任务标为 `SUCCESS` 并结束任务；明确不可自动恢复时按上一条暂停调度，仍保持失败状态。页面只保留基本退款状态和进度，不增加异常详情、异常处理或手动重试入口。后台日志与现有退款记录足以承载异常信息，不另建异常记录；后续若收到渠道确认成功的回调，仍可按幂等成功逻辑更新结果。
8. **核对兜底。** 对已取消课程持续分页核对已确认支付与退款记录，补齐遗漏任务；对用户自助取消依赖报名与退款任务同事务写入。不将课程已取消、退款请求已发出或某一批执行完毕视为全部退款完成。

## 8. 定时维护

`group_course_maintenance/config.json` 配置每分钟触发：

```json
{
  "triggers": [
    {
      "name": "group_course_maintenance_every_minute",
      "type": "timer",
      "config": "0 * * * * * *"
    }
  ]
}
```

每次分批处理，单批默认 50 条：

1. 扫描并结算超过 3 分钟的 `PENDING_PAYMENT`。
2. 扫描到达报名截止加 3 分钟最终判定时间的 `PUBLISHED` 课程，按第 7.6 节成班或自动取消。未决查单不能阻塞本项；每分钟调度造成的实际执行延迟不改变业务判定时点。
3. 扫描已结束的 `CONFIRMED` 课程并标记完成。
4. 核对已取消课程的已确认支付与退款记录，补做遗漏退款以及未完成的场地释放、占位失效，规则见第 7.7 节。分批处理需持续推进，不能每次只检查同一批记录。
5. 扫描 `PENDING`、`PROCESSING`、`FAILED` 中 `nextRetryAt` 非空且已到期、租约可领取的退款任务，按第 7.8 节提交或查询；不能只扫描失败退款。按到期时间和稳定文档 ID 分页推进，失败任务安排未来执行，不阻塞本批其他任务。

列表、详情和报名入口可以针对当前课程顺带执行轻量过期清理，作为定时触发器未部署或延迟时的兜底。所有处理必须使用条件状态更新和幂等键，允许定时任务重复执行。

## 9. 错误处理与一致性

- 云数据库事务只包含数据库读写；微信会员查询、统一下单、主动查单和退款调用均在事务外完成。
- 外部调用前先建立本地状态，调用失败后通过补偿事务或维护任务收敛。取消中断后由维护任务核对并补做遗漏退款；退款任务在第 7.8 节规定的租约、查询、幂等和重试机制下自动接续。明确不可自动恢复的渠道异常按第 7.8 节仅记录日志与现有退款状态并暂停调度，不新增异常处理流程。
- 所有支付和退款回调重复到达均返回成功，但只有符合前置状态的第一次调用能改变业务状态。
- `enrollmentVersion` 在每次报名状态变化时递增，使容量、最低人数和展示聚合能够检测陈旧快照。它不等于参与人数，也不与人数上限比较。
- 退款成功前不释放名额；退款失败不会恢复课程，也不会物理删除报名。
- 日志记录课程、报名、支付、退款 ID 和状态变化；手机号脱敏，不记录支付参数、数据库密码等敏感数据。

1. 检查并清理 `court_order_collection` 中重复的 `(campus, court_id)`。

## 12. 评审决策

本节记录 2026-09-05 评审确认的业务规则、范围取舍及据此补齐的设计细节。后续若业务规则变化，需同步修订相关模型、流程、维护与测试章节。

### 12.1 支付回调范围与成班判定

- 已确认：支付有效期 2 分钟，占位 3 分钟；正常支付按付款成功后 1 分钟内完成回调处理设计。
- 已确认：不采用“旧支付结果查不清就禁止重新报名”；3 分钟到期仍未确认成功即释放占位，符合报名条件时允许重报。
- 已确认：不增加旧报名轮次迟到付款的专门隔离、自动退款或跨轮次补偿流程；不继续将该问题列为必须重新设计的功能。
- 已接受范围限制：若上述回调假设失效，可能出现实际扣款与本地报名状态不一致；本期不提供该异常的自动收敛保证，按云服务或支付通知异常向相关服务商反馈排查。这是产品范围取舍，不代表厂商已承诺承担责任。
- 保留原有支付历史、按商户订单号定位和重复回调幂等，不另增轮次模型。
- 实现细节已补齐：报名 `paidAt` 保存本系统首次支付确认的数据库时间；成班聚合实际执行确认时状态为 `PAID` 的报名，不再按 `paidAt` 筛选，并在事务中用 `enrollmentVersion` 校验统计有效。重复回调不修改该时间，重报清空旧值，定时任务延迟时仍按执行确认时的当前付款人数判定。
- 已确认边界：成班判断不延长报名截止后的 3 分钟期限；正常流程中课程取消与支付确认并发仍按第 7.3 节退款且不恢复课程。

### 12.2 取消与退款中断恢复

- 已确认：用户曾遇到未能完全退款的情况，本期使用持久化退款任务加每分钟定时执行，自动补漏、查询和重试，不提供管理员手动重试按钮或接口。
- 已确定方案：复用 `group_course_refund` 保存任务，由现有 `group_course_maintenance` 执行；不额外部署独立消息队列服务。具体状态、领取、租约恢复、查询、幂等和自动退避见第 5.5、7.5、7.7、7.8、8 节。
- 已确认：以已取消课程的已确认支付记录核对退款任务，补齐遗漏；不能仅重试已有失败退款。场地释放与未支付占位失效也须可重复补做，单笔失败不阻塞其他退款。
- 已确认边界：课程取消不等待退款全部完成；用户自助取消仍在渠道确认退款成功后释放名额；“取消课程”暂不细分实际授课情况。
- 已确认：明确不可自动恢复的渠道异常只写后台日志，并在现有退款记录中更新 `FAILED`、渠道状态和错误字段，`nextRetryAt=null` 暂停自动调度。不新增异常集合、异常记录、异常详情页面、商户平台处理指引或管理员处理入口；不将暂停调度描述为退款成功。
- 临时失败继续自动重试，未决结果继续自动查询；上述暂停仅适用于渠道明确不可自动恢复的情况。

### 12.3 教学内容模板与具体课程的边界（已确认）

- 最晚发布时点为报名截止前；本期仅付费课，原价整数元且折后至少 1 元；基础资料直接在云数据库维护，不新增管理页面。
- 教学内容模板独立存入 `group_course_template`，只负责“这节课教什么”，包含标题和教学详情；管理员选择后将其填入具体课程。
- 课时时长、原价、最低人数、人数上限、日期、时间、教练、校区和场地全部属于具体课程。本节撤销此前将时长、价格和人数列为模板候选字段的建议。
- 具体课程通过 `templateId` 记录内容来源，同时保存自身 `title`、`description` 等数据。模板后续修改不会自动更新具体课程，发布前调整表单不回写模板。
- 模板仅在新课程表单中填充教学内容；发布前切换模板只替换标题与教学详情，不覆盖其他开课信息，发布后禁止修改课程。

### 12.4 一次性发布并占场（最终规则）

- 管理员填写新课程表单，发布前弹框确认关键信息，点击“确认发布”后由服务端原子创建正式课程并占用全部时段。
- 页面填写和弹框查看阶段不创建课程记录、不占场；系统没有 `DRAFT`、`DELETED` 状态，也没有 `saveDraft`、`deleteDraft` 或课程编辑接口。
- 发布前可以在当前表单调整内容，每次调整后重新确认；发布后全部内容不可修改，需要变更时整体取消后重新发布。
- 发布失败不留下课程或部分占场，当前页面保留输入；发布结果未明时用同一请求标识核实，防止重复发布。
- 不需要未发布课程的保留期限、超时释放或换场机制。本节取代此前保存即占场的方案。


## 手机号业务身份原则（2026-09-06 明确）

登录状态、管理员权限、VIP 资格、报名唯一性、本人记录与退款归属均以手机号判断，复用个人中心已有手机号及资料。不以 openid 判断上述业务身份，不增加独立 token、微信身份绑定表或重复授权。本期沿用现有畅打对客户端手机号的信任方式，用户已明确接受这一业务取舍。

团课前端不读取或传递 openid 作为登录资料。支付网关中的 openid 仅为 JSAPI 下单参数，从云函数微信上下文取得；维护入口检查调用上下文用于区分客户端调用与定时触发，不参与手机号业务判断。上述技术用途不构成另一套登录机制。

对客户端完整性的信任属于本期采用的业务假设，本文不将其表述为已核实的微信平台“不可篡改、不可伪造”技术保证。


### 数据源核对结果

团课只复用 CloudBase manager（人员与权限）、court（场地）、court_order_collection（占场），新增 campus 与五个 group_course* 集合。MySQL prepaid_card 仅只读 VIP；MySQL coach/court/course 属于旧教练与课耗模块，不与本功能混用 ID 或记录。manager 里有姓名和手机号的记录均可作为授课候选，候选资格不代表团课创建权限；只有 courtRushManager>=1 或 specialManager>=1 可创建。manager 的密码、手机号及权限字段不会随候选列表返回，列表只返回 id/name/introduction。


### VIP 价格查询与支付（当前实现）

团课复用订场已有 club_member 云函数，以手机号判断 rest_charge + annual_count×150 + times_count×150 > 0。不由 manager_permissions 提供 VIP。list/detail 为价格展示查询，enroll 为本次报名实时查询；context/publish/cancelEnrollment/cancelCourse 不查询 VIP，其 viewer.isVip 为 null（未查询，不表示非 VIP）。未登录游客按原价展示。查询异常不能按非 VIP 悄悄扣款。

报名返回并保存实际 isVip 与 actualFeeYuan；VIP 实付为课程手填的 vipPriceYuan，支付渠道金额为 actualFeeYuan×100。前端展示实际价格，若与页面原报价不同则再次确认后才调用微信支付。已有有效报名的重复请求复用原付款与金额快照，不因会员变化改写已生成订单。团课四函数只依赖 wx-server-sdk，无须配置 DB_*，这些配置继续由已有 club_member 管理。

### 2026-09-06 手填价格与默认场地决策

用户确认VIP直接填金额；尚未发布正式课程，无需迁移或兼容旧八折课程。发布请求摘要、CourseDTO、列表详情和报名同步使用vipPriceYuan；付款退款沿用报名金额快照。默认场地不新增集合、索引或独立资源锁。部署需同步更新小程序及四个团课云函数。
